# 出力／ゴミ注釈 (`out` annotation) の設計

## 1. 動機

Janus のプログラムは終端の記憶域**全体**が出力である。言語には「どの変数が結果か」を
述べる構文がなく、RC-03（資源アトラス）もこの理由で `final_live_bits` を量として
報告するにとどめている：

> 終端の状態が不要なゴミか出力かの判定はしない．Janus では終端の記憶域全体が出力であり，
> どの変数が出力かは注釈なしには決まらないためである．（rc03 §method）

その結果、見出しの数字

> 書き込みのあった配列の約 65% は値を戻す操作を持たず，終端で空になる配列は約 13% にとどまる．

は、**正当な出力**（`counting_sort` の `b`、`knapsack` の `K`）と**ゴミ**（`selection_sort`
の `ftab`、`kmp` の `f`、`dijkstra` の `visited`）を区別せずに数えている。
本文書は (i) 将来の方言拡張としての表層構文と、(ii) パーサを変えずに今日使える
注釈形式（構造化コメント＋サイドカー）を定め、(iii) 終端での配列の判定手続きを与える。

用語：本文書で **ゴミ (garbage)** とは「終端で非 0 だが、注釈で出力と宣言されていない
変数」を指す。可逆性のために残さざるを得ない履歴（分岐ログのスタック、上書き前の値）も
含む。Bennett の意味での「消去できないゴミ」と、単に片づけ忘れた中間結果とを区別する
のは注釈の**理由付け**（rationale）の役目であり、分類そのものは区別しない。

## 2. 表層構文（将来の方言拡張）

### 2.1 形

```
procedure p(int a[], out int r[], stack gb)        // 手続きの仮引数
procedure q(in int wt[], in int val[], int n, int cap, out int K[])

procedure main()
  int wt[4]
  out int K[24]                                    // main の宣言
  stack gb
```

- `out T x` : x は**出力**。終端で非 0 であることが期待される。
- `in T x`  : x は**入力**。終端で初期値（main の初期化直後の値）と一致することが期待される。
- 無印       : どちらでもない。終端で非 0 なら**ゴミ**、全 0 なら**クリーン**。
- `in out` は認めない（その場所で入力を消費し結果を置く「その場書き換え」は `out`）。

`in`/`out` は型の一部ではなく**宣言修飾子**であり、実行時意味論を一切変えない
（`ast.py`・`runtime.py` に手を入れずに、パーサが修飾子を読み飛ばすだけで既存の全
フィクスチャが今まで通り動く）。

### 2.2 プログラム水準の分類は main で決まる

分類は **main の宣言**で決まる。手続きの仮引数の `out` はそれ自身では何も出力しない：

- 呼び出し `call p(x, y, gb)` で、`p` の `out` 仮引数 `r` に main の無印変数 `y` が
  結合された場合、`y` はプログラムの観点では**依然ゴミ**である（`p` の局所的な出力が
  プログラムの出力になるかどうかは main が宣言する）。
- 逆に `out` 宣言された main 変数を、無印の仮引数に渡しても出力のままである。
- 仮引数の `in`/`out` は、呼び出しごとに main の分類と突き合わせて**警告**を出すための
  型検査の材料（§6）であり、分類の入力ではない。

### 2.3 `uncall` による反転

`uncall p(...)` は `p` の本体を反転して実行する。このとき `p` の仮引数の
`in`/`out` は**入れ替わる**：

| 仮引数の宣言 | `call` での役割 | `uncall` での役割 |
|---|---|---|
| `out T r` | 0 → 結果を書く | 結果 → 0 に戻す（消費） |
| `in T a`  | 読み取り専用 | 読み取り専用 |
| 無印      | 任意 | 任意 |

`in` は自己双対（読み取り専用は逆向きでも読み取り専用）。`out` の双対は
「消費（0 に戻す）」であり、`bubble_sort.ja` の `uncall bsort(ord,sz,gb)` がその例：
`bsort` の `gb` を `out stack gb` と宣言すれば、`call` で満たされ `uncall` で空に戻る。
プログラム水準では `ord` が `out`、`gb` は無印で終端で空（クリーン）になる。

### 2.4 意味（終端における）

main の変数 x について、終端の記憶域 σ_end と初期化直後の記憶域 σ_0 を用いて：

| 宣言 | 期待される終端条件 | 破られたときの分類 |
|---|---|---|
| `out x` | σ_end(x) ≠ 0 | **clean**（出力なのに空）＋不一致警告 |
| `in x`  | σ_end(x) = σ_0(x) | **garbage** ＋不一致警告（`takes>0` で検出可能な範囲） |
| 無印 | — | σ_end(x) ≠ 0 なら **garbage**、= 0 なら **clean** |

## 3. 今日使える形：構造化コメント＋サイドカー

### 3.1 構造化コメント

パーサの前段、**文字列水準**で読む（`jana_py/outannot.py: parse_comment_annotations`）。
コメントなのでどの方言でも解析結果に影響しない。

```
// @out: K, res
// @in: wt, val, x[], y
// @garbage: gb, dlog
// @scratch: tmp
```

- 1 行 1 タグ、名前は `,` か空白区切り。末尾の `[]` は無視する。構造体フィールドは
  `a.v` のようにドットで書く。`/* @out: ... */`（1 行）も可。
- `@out`/`@output`, `@in`/`@input`, `@garbage`/`@gb`, `@scratch` を受け付ける。
- 同じ名前に異なる役割を与えると `AnnotationError`（`strict=False` で後勝ち）。
- 位置はファイル先頭または `main` 直下を推奨するが、どこでもよい。
- `@scratch` は「終端で 0／空に戻る予定」の宣言。§4 の判定では `@garbage` と同じ扱いで、
  非 0 のまま残っていれば不一致警告を出す。

### 3.2 サイドカー

フィクスチャを編集したくないプログラムには
`tests/resource_atlas/annotations/out_annotations.json` を用いる（101 本の手注釈。
フィールドは同ディレクトリの README.md）。読み込みは `load_sidecar()`、
プログラムへの対応付けは `sidecar_for()`（リポジトリ相対パス完全一致 → パス末尾一致 →
basename 一致、`fib.ja` のように複数方言に同名がある場合は `tests/jana2014/...` 優先）。
ソース内コメントとサイドカーの両方があるときは**コメントが優先**（`annotation_for_program`）。

## 4. 終端における配列の判定手続き

入力：資源プロファイラが配列ごとに出す 4 値
（`puts` = 0→非0 の回数、`takes` = 非0→0 の回数、`ends_empty` = 終端で全セル 0、
`written` = 書き込みがあった）と注釈の役割。出力：4 クラスのひとつ。

```
classify_one(name, {puts, takes, ends_empty, written}, role):
  if ends_empty:                    -> clean
       (role ∈ {output, input} なら不一致警告)
  elif role == output:              -> output
  elif role == input:               -> input-preserved
       (takes > 0 なら「変更後に復元」の注記)
  else (garbage / scratch / 無注釈): -> garbage
       (scratch なら不一致警告、無注釈なら "unannotated" 注記)
```

注意点：

1. **`written` は入力配列も真になる。** 入力は main で `adj[i] += 1` のように初期化される
   ので `puts > 0`。RC-03 の「書き込みのあった 189 本」は入力配列を含んでおり、
   「値を戻す操作を持たない 65%」の中に *入力そのまま* が混ざっている。
   再集計では `takes == 0` の配列を output / input-preserved / garbage に三分する。
2. `input-preserved` は注釈を信用する。プロファイラの 4 値からは「初期値と一致」を
   確認できない（`takes == 0 ∧ puts == 初期化回数` は必要条件にすぎない）。
   厳密な確認には σ_0 と σ_end の比較が要る（§6）。
3. 配列の**一部**だけが出力（DP 表の 1 セル、`matrix_apsp` の `m_arr[32..47]`）である
   場合、配列単位の分類では `output` とし、サイドカーの `confidence` を `medium` に
   落として rationale に書く（table-as-output caveat）。セル単位の分類は将来課題。
4. スタックは配列と同じ 4 クラスで扱う（`ends_empty` = 空）。分岐履歴を持つ
   `gb`/`log`/`blog` は、ヘッダが出力と明言していなければ garbage
   （rationale に「reversibility log」と記す。`convex_hull` の `hseq` は出力）。

## 5. Bennett 埋め込みと `erasures ≡ 0` との関係

- **Bennett 埋め込み**（`jana_py/bennett.py: bennett_embed(stmts, output_map, input_vars=...)`）
  は `output_map` で結果変数を、`input_vars` で入力変数を指定して
  compute–copy–uncompute を生成する。これは本注釈の `out`/`in` と**同じ情報**である：
  `out` 集合 = `output_map` の値域、`in` 集合 = `input_vars`。
  したがって `@out`/`@in` を持つプログラムは、追加情報なしに Bennett 埋め込みの
  入力になる。埋め込み後は、無印の変数（ゴミ）は補助変数 `anc__*` に改名されて
  `local … delocal` で 0 に戻り、終端に残るのは `in`（不変）と `out` のみになる。
  すなわち **注釈に対して「ゴミ = ∅」が Bennett 埋め込みの正しさの検証条件**であり、
  `classify` を埋め込み前後に適用すれば garbage の本数が 0 に落ちることを機械的に確認できる
  （手数は増える：rc03 §baseline「同じ計算をクリーンに行えば手数は 3.3 倍」）。
- **`erasures ≡ 0`** は言語の定義から常に成り立つ（不可逆消去がない）。注釈はこの
  不変量に触れない：ゴミを「消す」のではなく「ゴミと呼ぶ」だけである。RC-03 の
  問い「補助的に使われた記憶が片づけられるか」に対し、注釈は分母（書き込みのあった配列）
  から出力と入力を除いた**片づけ得た配列**を分離する。`erasures = 0` かつ
  `garbage > 0` が「消去せずに残した」量、`clean` が「逆計算で片づけた」量になる。

## 6. 将来課題

1. **`out` の型検査。** (a) `out` 変数は宣言後、それを 0 に戻す `uncall` の引数に
   なってはならない（出力を消費する = プログラムの出力ではない）。(b) 手続きの
   `out` 仮引数に結合された main 変数が無印ならば警告（局所的な出力がプログラム水準では
   ゴミになっている）。(c) `in` 仮引数に結合された変数を本体が書き換えていれば誤り
   （`_collect_modified_vars` の拡張で静的に検出可能。現行は Call/Push/Pop を追わない）。
   (d) `in` 変数は main で初期化以外に書かれてはならない。
2. **σ_0 と σ_end の比較**による `input-preserved` の実測確認（プロファイラに
   初期化直後のスナップショットを 1 枚追加すれば足りる）。
3. **セル単位の分類**（DP 表の答えのセルと履歴セルの分離）。
4. **パーサ拡張**：`in`/`out` 修飾子を jana2014/janus2026 の宣言と仮引数で読み飛ばし、
   `Program` に付随する `annotations` 辞書へ落とす（`ast.py` の変更は付随辞書のみに
   限定できる）。
5. スカラーの `final_live_bits` への同じ分割（サイドカーの `scalars_out` は既にある）。
